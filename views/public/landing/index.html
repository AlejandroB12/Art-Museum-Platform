Arquitectura Políglota

DoArt Magic es un museo digital, basado en una arquitectura de microservicios robusta, donde su core transaccional opera sobre cuatro motores de base de datos simultáneamente. PostgreSQL, MongoDB, CassandraDB y Neo4j, estas bases de datos conviven detrás de un mismo API Gateway, cada una resolviendo la necesidad para la cual fue diseñada. Modernidad, estilo, integración poliglota y una arquitectura sólida es lo que nos define.

04 · Justificación Teórica

Teorema CAP: ¿por qué cada nodo eligió su bando?

Cada base de datos fue seleccionada según su posición en el teorema CAP. Navega por los motores para entender la decisión detrás de cada uno.

CP

PostgreSQL — Core Transaccional

Facturas, inventario de obras y estado de reservas exigen Consistencia antes que disponibilidad: dos compradores no pueden pagar por la misma obra.

Prioriza Consistencia y Tolerancia a Particiones, sacrificando disponibilidad en caso de partición de red — bloquea escrituras antes que arriesgar un doble cobro.

AP

Cassandra — Auditoría y Reportes

La bitácora de seguridad y los resúmenes de facturación deben poder escribirse siempre, incluso si un nodo del clúster cae.

Prioriza Disponibilidad; acepta consistencia eventual entre réplicas porque un reporte gerencial puede tardar en reflejar el último evento sin romper nada crítico.

AP

MongoDB — Catálogo

El catálogo público debe seguir sirviendo obras aunque haya latencia entre réplicas. Los esquemas polimórficos se benefician de la flexibilidad documental.

Prioriza disponibilidad sobre consistencia estricta inmediata — es aceptable que un usuario vea datos ligeramente desactualizados mientras la réplica se actualiza.

CP

Neo4j — Grafo de Recomendaciones

Las relaciones (Comprador)-[:COMPRO]->(Obra)<-[:CREO]-(Artista) necesitan integridad referencial fuerte.

Los recorridos de recomendación no pueden devolver nodos huérfanos o inconsistentes. Prioriza Consistencia sobre disponibilidad para preservar la integridad del grafo.

05 · Plan de Tolerancia a Fallos

¿Qué pasa cuando un microservicio cae?

Caída de Recomendaciones (Neo4j)

El Gateway captura el timeout y el catálogo se sirve sin la fila de recomendados — degradación elegante, no error 500 para el usuario final.

Caída de un nodo Cassandra

Con QUORUM (2 de 3 réplicas) las escrituras de auditoría siguen aceptándose; solo se pierde tolerancia si caen 2 nodos simultáneamente.

Partición de red hacia PostgreSQL

El core transaccional prioriza Consistencia: ante duda, bloquea la escritura de una compra antes que arriesgar un doble cobro. El usuario ve "intenta de nuevo".

Fallas bizantinas (nodo comprometido)

Mitigación vía consenso PBFT entre réplicas de auditoría: una escritura solo se considera válida si 2f+1 de los 3f+1 nodos coinciden, tolerando hasta f nodos bizantinos.

07 · Robustez y Seguridad

Una arquitectura pensada para producción

Cada capa del sistema incorpora mecanismos de seguridad, resiliencia y auditoría desde el diseño.

🔐

Autenticación y Autorización

JWT con refresh tokens, bcryptjs para hash de contraseñas, preguntas de seguridad como segundo factor. Cada microservicio valida el token contra el Gateway antes de procesar cualquier petición.

🛡️

Rate Limiting y DDoS

El Gateway implementa rate limiting por IP y por ruta, con backpressure controlada vía middleware. Las conexiones a bases de datos usan pool limitado para evitar agotamiento de recursos.

📋

Auditoría Inmutable (Cassandra)

Toda operación crítica queda registrada en una bitácora solo-append en Cassandra: inicios de sesión, cambios de estatus de obras, transacciones financieras. Escritura siempre disponible incluso bajo partición de red.

⚡

Tolerancia a Fallos

Degradación elegante ante caída de microservicios: el catálogo se sirve sin recomendaciones si Neo4j falla, las escrituras de auditoría continúan si un nodo Cassandra cae (QUORUM 2/3), y PostgreSQL bloquea escrituras antes que permitir un doble cobro.

🔒

Cifrado en Tránsito y Reposo

Todas las conexiones entre microservicios y bases de datos utilizan TLS/SSL. Las contraseñas se almacenan con bcryptjs (salt rounds = 12) y los datos sensibles en PostgreSQL usan cifrado a nivel de columna.

📊

Monitoreo y Alertas

Cada microservicio expone métricas en formato Prometheus. El Gateway centraliza logs estructurados y tiempos de respuesta. Alertas ante picos de latencia, tasas de error elevadas o caída de nodos de base de datos.
