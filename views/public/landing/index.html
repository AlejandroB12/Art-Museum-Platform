Arquitectura Políglota

DoArt Magic es un museo digital que usa cuatro bases de datos distintas trabajando juntas: PostgreSQL, MongoDB, Cassandra y Neo4j. Cada una hace lo que mejor sabe hacer, y todas se comunican a través de un único punto de entrada. Esto nos da velocidad, seguridad y flexibilidad.

04 · Justificación Teórica

Teorema CAP: ¿por qué cada nodo eligió su bando?

El Teorema CAP dice que una base de datos solo puede cumplir bien dos de tres cosas: Consistencia, Disponibilidad o Tolerancia a Particiones. Aquí te explicamos qué eligió cada motor y por qué.

CP

PostgreSQL — Pagos y reservas

Las facturas, el inventario y las reservas necesitan que los datos sean correctos siempre: si dos personas compran la misma obra, solo una debe pagar.

Elige Consistencia ante todo. Si hay una falla de red, prefiere detener la compra antes que permitir un error que duplique el cobro.

AP

Cassandra — Registro de actividades

La bitácora de seguridad y los reportes de facturación deben poder seguir escribiéndose aunque un nodo del clúster se caiga.

Elige Disponibilidad. Acepta que los datos se actualicen con unos segundos de retraso (consistencia eventual), porque un reporte puede esperar, pero no puede dejar de guardarse.

AP

MongoDB — Catálogo de obras

El catálogo debe seguir funcionando aunque haya demoras entre las copias de los datos. Además, cada obra puede tener características distintas (polimorfismo).

Elige Disponibilidad. Es aceptable que un usuario vea datos ligeramente desactualizados mientras la réplica se actualiza, porque lo importante es que el catálogo nunca deje de verse.

CP

Neo4j — Recomendaciones

Las conexiones entre compradores, obras y artistas deben estar siempre bien relacionadas. Una recomendación no puede mostrar datos incorrectos.

Elige Consistencia. Los recorridos de recomendación necesitan integridad total: si la base de datos dice que un usuario compró una obra, esa relación debe ser verdadera siempre.

05 · Plan de Tolerancia a Fallos

¿Qué pasa cuando un microservicio cae?

Caída de Recomendaciones (Neo4j)

El catálogo se muestra sin recomendaciones si Neo4j falla. El usuario no ve un error, solo menos contenido.

Caída de un nodo Cassandra

Cassandra tiene 3 copias de cada dato. Mientras al menos 2 estén funcionando, las escrituras continúan. Solo falla si se caen 2 nodos a la vez.

Partición de red hacia PostgreSQL

Si hay una falla de red, PostgreSQL prefiere bloquear una compra antes que arriesgarse a cobrar dos veces. El usuario ve un mensaje para que intente de nuevo.

Fallas bizantinas (nodo comprometido)

Si un nodo es comprometido, los demás verifican la información entre ellos. Una escritura solo se acepta si la mayoría de los nodos están de acuerdo.

07 · Robustez y Seguridad

Una arquitectura pensada para producción

Cada parte del sistema está diseñada para ser segura, tolerante a fallos y fácil de monitorear.

🔐

Autenticación y Autorización

Usamos JWT con tokens de actualización, contraseñas encriptadas con bcryptjs y preguntas de seguridad como segundo factor. Cada microservicio verifica la identidad del usuario antes de procesar cualquier solicitud.

🛡️

Rate Limiting y DDoS

El Gateway limita las solicitudes por IP y por ruta para evitar ataques. Las conexiones a las bases de datos también están controladas para no saturarlas.

📋

Auditoría Inmutable (Cassandra)

Cassandra guarda un registro permanente de cada acción importante: inicios de sesión, cambios en obras y transacciones. Una vez escritos, estos datos no se pueden modificar.

⚡

Tolerancia a Fallos

Si un microservicio falla, el sistema se adapta: el catálogo se muestra sin recomendaciones si Neo4j no responde, las auditorías siguen escribiéndose si un nodo de Cassandra falla, y PostgreSQL detiene una compra antes que cobrar de más.

🔒

Cifrado en Tránsito y Reposo

Todas las comunicaciones entre servicios usan cifrado TLS/SSL. Las contraseñas se guardan con bcryptjs y los datos sensibles se encriptan directamente en la base de datos.

📊

Monitoreo y Alertas

Cada servicio expone métricas de rendimiento. El Gateway centraliza los registros y envía alertas cuando hay demoras, errores o caídas en las bases de datos.
